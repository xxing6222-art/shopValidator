# 店判：从 AdventureX 评分函数到餐饮开店与止损 Agent

> 结论先行：不要做“帮餐厅提高营业额”的通用顾问。应做一个在签租约、交转让费、加盟、装修、继续烧钱之前，强制收集证据并给出 `GO / TEST / STOP / EXIT` 闸门的决策 Agent。

## 2. AdventureX 实际评分函数

### 2.1 能确认的官方标准

AdventureX 2025 没有一张覆盖所有项目的统一数值评分表。官方项目库列出多个主题赛道和赞助赛道，各赛道自行定义要求。例如飞书赛道明确按“AI 创新性、实用性、产品价值、完成度、使用体验”五个方向评分；PPIO 赛道要求必须使用其 AI 产品。[AdventureX 2025 官方赛道页](https://gallery.adventure-x.org/tracks?event=advx-2025)、[PPIO Phantom Hunter 赛道](https://gallery.adventure-x.org/tracks/phantom-hunter-ai-agent?event=advx-2025)

所以“官方唯一评分公式”不存在。能从多个赛道共同提炼的是：

- 问题与产品价值；
- AI 或赞助技术是否真正参与核心链路；
- 能否运行，而不是只有概念；
- 稳定性与完成度；
- 使用体验和演示表达；
- 赛道契合与复用潜力。

### 2.2 根据比赛结构推导的评分卡

下表是为了选题和做 Demo 构造的推导评分卡，不冒充官方规则：

|维度|分值|本项目如何拿分|
|---|---:|---|
|真实问题与损失证据|20|真实连麦语料；把失败定义为下一笔不可逆损失|
|端到端完成度与稳定性|20|表单输入、财务计算、压力测试、决策闸门全部本地可运行|
|AI / 系统不可替代性|15|多模态取证、主动追问、合同核验和长期状态，不是一次问答|
|30 秒 Demo 清晰度|15|输入店铺数据后立刻出现保本线、现金寿命和 STOP/TEST|
|赛道与赞助技术契合|15|地图、视觉、OCR、Agent、结构化工作流均有自然位置|
|差异化与技术表达|10|“证据不足就拒答”，确定性计算和模型推理分层|
|结果可量化与可延伸|5|避免投入金额、实验后决策变化、14 天执行结果|
|合计|100||

还有两个不应写进加分表、但现场会决定生死的硬门槛：

- 评委在 30 秒内能听懂“原来要再投 20 万，现在先花 800 元验证”；
- 断网或模型失败时，核心财务计算和样例路径仍能演示。

标题会追求戏剧性，这个统计只能说明频道叙事聚焦“亏钱、重投入、加盟”，不能直接等同于真实连麦动机。

### 3.2 对话中的表面请求

表面请求确实经常是：

- “新店开业想提升下营业额”；
- “就是想提升一下营业额”；
- “想要让你分析一下思路”；
- “店前人流不断，为什么没人买”。

例如成都案例明确以“提升营业额”开场，勇哥随即追问日销、毛利和人工，而不是先推荐投流。[成都案例字幕](../bilibili-ai-subtitles/srt/BV12pTq6qEjQ.srt)

### 3.3 真正的共同任务

这些老板缺的不是一句营销创意，而是一套反沉没成本的决策机制：

> 在数据残缺、情绪上头、总部催签、装修已经开始或现金持续流失时，判断下一笔不可逆的钱该不该花。

“提高营业额”只是用户说得出口的 solution request。底层 job 是：

1. 我的单店模型是否在数学上可能成立？
2. 是没人经过，还是经过的不是目标客群，还是看不见、看见不进、进店不买？
3. 亏损能否通过一个可验证的局部改变修复？
4. 如果不能，何时停止、缩店、转让或退出？
5. 在加盟、转让和装修之前，有没有更便宜的验证办法？

最简洁的证据来自提拉米苏摊位案例：勇哥直接区分“有人流”和“有客流”，再指出转化率、可见性和产品呈现问题；随后才核对毛利与房租。[提拉米苏案例字幕](../bilibili-ai-subtitles/srt/BV16FNP64EH4.srt)

### 3.4 从第一性原理重新定义需求

餐饮老板并不真正需要“更多经营知识”。通用模型、短视频和加盟总部已经能提供大量建议。真正稀缺的是：在信息不完整、账目混乱、沉没成本和时间压力同时存在时，仍能做出一项可退出的决定。

把用户目标写成“营业额最大化”会把产品带向投流、团购和营销建议；更准确的目标函数是：

```text
保住的家庭与经营现金
+ 避免的不可逆错误投入
+ 通过低成本实验获得的信息
+ 保留下来的退出选择
− 继续经营、验证和退出的成本
```

这解释了为什么全量标题中“增长诉求”只有 6.6%，而“亏损与现金流”达到 49.8%、“投入过重”达到 37.9%。用户嘴上可能问“怎么多卖”，实际面对的是五类问题：

1. **不知道自己是否真的赚钱。** 营业额、毛利、人工、老板工资、房租和现金储备没有放进同一张账；
2. **不知道客流链路断在哪里。** 人多不等于目标客群多，目标客群经过也不等于能看见、看懂、进店、下单和复购；
3. **无法抵抗沉没成本。** 已经交的钱、总部承诺和朋友意见，被错误地当作继续投入的理由；
4. **在不可逆节点前缺少证据。** 签租约、交转让费、加盟、装修和追加投资都比一次小测试昂贵得多；
5. **没有停止线。** 即使连续亏损，也没有预先写明何时缩减、转让或退出。

因此，产品的核心任务不是“替老板想一个好点子”，而是：

> 在下一笔不可逆付款之前，用最低的输入成本补齐最关键证据，算清最坏结果，并给出一个可执行、可复查、可退出的决定。

### 4.1 实际协议

可以把他的隐性协议还原为六步：

#### 第一步：让镜头“转一圈”

- 在哪个城市、哪个商圈；
- 主要入口、道路、地铁、小区、景区或写字楼在哪里；
- 门头多宽、从主要方向是否可见；
- 店铺面积、楼层、入口和内部动线；
- 相邻店铺与真实竞争者是谁。

待开咖啡店案例中，连麦者说“还没开始做”，勇哥先让他后退展示现场，然后确认城市、面积、月租、加盟费和总部是否看过位置。[待开咖啡店案例字幕](../bilibili-ai-subtitles/srt/BV1VUMn6zEjq.srt)

#### 第二步：确认到底卖什么、卖给谁

- 具体品类和核心产品；
- 价格带与客单；
- 是旅游客、社区客、学生、白领，还是聚会人群；
- 消费者为什么现在、在这里、选这家而不选隔壁。

福州菜案例的后段，判断落到“想清楚消费者需要什么”；景区游客以 2—4 人为主时，过高的试错成本会压制首次消费。[福州菜案例字幕](../bilibili-ai-subtitles/srt/BV1GxKU6GEjJ.srt)

#### 第三步：把账算完整

- 当前日营业额和营业天数；
- 真实综合毛利，而不是某个招牌单品毛利；
- 房租、物业、仓库；
- 人工、社保、宿舍，并给老板本人计工资；
- 水电燃气、平台抽佣、推广等；
- 初始投入、转让费、加盟费、债务和现金储备。

福州菜案例在开场约两分钟内依次确认日销、毛利、面积、房租物业、人员数量与人工成本。[福州菜案例字幕](../bilibili-ai-subtitles/srt/BV1GxKU6GEjJ.srt)

#### 第四步：找到转化链路断点

```text
目标人群经过
  → 看见门头和产品
  → 理解卖什么、价格怎样
  → 愿意进店
  → 愿意下单
  → 产品与服务兑现承诺
  → 愿意复购或推荐
```

“人流”只是第一步；任何一段断裂，都可能让加大投流变成浪费。

#### 第五步：比较继续投入与退出的机会成本

- 保持现状每月亏多少；
- 现金还能支撑几个月；
- 达到保本需要多少日销和订单；
- 悲观情境下会发生什么；
- 是换产品、缩面积、改变时段、换渠道，还是直接停止；
- 继续做的时间是否比回去就业或做别的项目更值钱。

#### 第六步：只批准最便宜、可逆的下一步

- 证据充分、保本可行，才允许继续；
- 关键事实未知，就先做三天计数、摊位、预售或门头 A/B 测试；
- 数学上明显不可行，就停止新增投入；
- 现金寿命过短且修复路径未经验证，就进入退出准备。

这一步把“建议”变成 `GO / TEST / STOP / EXIT` 四种行动。每个结果都必须同时附带：

- 现在只做的一件事；
- 花费和时间上限；
- 成功标准；
- 到线后不再解释的停止条件。

## 5. 软件应该解决的根本问题

### 5.1 产品定义

**产品名：店判**

**一句话：** 餐饮开店与止损决策 Agent，用用户当前位置、少量关键账目和三个现场问题，在签租约、交转让费、加盟、装修或继续烧钱之前给出分阶段决策闸门。

**不做：**

- 又一个“问我怎样提高营业额”的聊天框；
- 凭一个地址就宣称能预测营业额；
- 搜不到真实转让费时编造一个市场均价；
- 用 LLM 计算保本点；
- 在证据不足时输出看似专业的长建议。

**要做：**

- 默认使用用户当前位置，自动补齐地址、行政区和附近公开地点；
- 只询问地图和系统无法知道的账目与现场事实；
- 主动问最能改变决策的下一道问题；
- 让用户拍摄店外、入口、门头、菜单和店内；
- 将地图 POI、合同、账单和现场计数放在同一个案卷；
- 用确定性公式计算保本线、订单量、现金寿命和压力场景；
- 明确区分事实、用户自报、模型推断和未知项；
- 输出 `GO / TEST / STOP / EXIT`，以及下一项低成本实验；
- 14 天后回收结果，判断建议是否真正减少损失。

### 5.2 为什么不能做成泛餐饮顾问

窄门餐谋已经公开覆盖品牌分析、品类趋势、选址、单店盈利、加盟风险和供应商搜索，并接入其餐饮品牌开关店数据。它还明确以“餐饮垂直数据优于 ChatGPT / DeepSeek”作为卖点。[窄门餐谋官方页](https://www.canyandata.com/canmou/)

因此，下面这句话不是差异化：

> “我做一个懂餐饮、可以问选址和利润的 AI。”

真正差异化应是：

|窄门餐谋公开定位|店判要占据的位置|
|---|---|
|输入问题，获得专业回答|系统主动要求现场和财务证据|
|行业数据库与经营知识|单店现场案卷与不可逆决策闸门|
|帮助选址、测利润、看品牌|明确何时不能签、不能投、应该退出|
|聊天式持续追问|确定性计算＋证据缺口＋可逆实验|
|“告诉你怎么做”|记录决策，14 天后核验结果|

## 6. 数据能否获得

### 6.1 地理位置、入口和附近业态

产品默认请求用户当前定位，不再让用户从省市区开始填写。浏览器返回 WGS84 坐标后，服务端先调用腾讯位置服务坐标转换接口转为 GCJ-02，再调用逆地址解析和周边地点搜索。附近搜索以当前位置为中心，在 800 米内按用户填写的餐饮品类返回公开地点；腾讯接口也可以返回部分 POI 的子点位或出入口信息。[腾讯地图 JavaScript API GL 指南](https://lbs.qq.com/webApi/javascriptGL/glGuide/glBasic)、[腾讯位置服务地点搜索文档](https://lbs.qq.com/service/webService/webServiceGuide/search/webServiceSearch)、[腾讯位置服务逆地址解析文档](https://lbs.qq.com/service/webService/webServiceGuide/address/Gcoder)、[腾讯位置服务坐标转换文档](https://lbs.qq.com/service/webService/webServiceGuide/translate)

地图密钥只保存在服务端，不进入网页。定位失败、用户不在店内或接口不可用时，允许只填“城市＋商圈或地址”继续；系统必须明确标注地图数据没有参与判断，不能用模拟数据伪装成功。

但地图 POI 不能告诉系统：

- 人从哪个门真正出来；
- 门头被树、围挡或楼梯遮住；
- 晚上是否看得见；
- 经过者是不是目标客群；
- 一百个经过者有几个人进店。

所以地图只能生成假设，必须由现场视频和分时段计数验证。即使地图返回了某个“入口”，也不能推断顾客实际从哪里来，更不能把附近同类店数量换算成营业额。

### 6.2 转让费

不存在可靠、完整、实时的全国转让费公共数据库。软件不应伪造“附近真实转让均价”。可行方案是：

1. 用户上传转让报价、租约和公开挂牌链接；
2. 保存来源、发布时间和可比性；
3. 将转让费视作不可逆投入；
4. 反算在保守现金流与剩余租期下，最多承受多少；
5. 数据不足时只给范围和不确定性，不给伪精确数字。

### 6.3 加盟品牌和合同

商务部的商业特许经营系统可按公司、品牌、经营资源或备案号查询备案。官方还建议结合国家企业信用信息公示系统、裁判文书等核查；特许人依法应在签约至少 30 日前书面提供费用、经营网点、审计报告、诉讼仲裁等信息。[商务部：如何鉴别特许人和特许项目](https://txjy.mofcom.gov.cn/manager/news.do?method=view&securityEntityId=BECC7629F227FB83FBBB9DCEAF035D8F)

产品可以把这些要求转化为合同核验清单，但不能代替律师出具法律意见。

## 7. 产品架构

```text
浏览器当前位置 / 少量关键账目 / 三个现场答案
                    ↓
   腾讯地图补地址与周边线索 / 来源标记
                    ↓
     ┌──────────────┴──────────────┐
     ↓                             ↓
确定性财务引擎                  Agent 追问器
保本、现金寿命、压力测试        找最高信息量缺口
     └──────────────┬──────────────┘
                    ↓
           风险假设与低成本实验
                    ↓
          GO / TEST / STOP / EXIT
                    ↓
             14 天执行结果回收
```

必须把两类工作分开：

- **公式与规则**负责可审计计算；
- **模型**负责从非结构化材料提取、识别矛盾、安排下一问和解释结果。

LLM 不直接控制财务数字，也不在数据缺失时补值。

## 8. 黑客松 MVP 与真实产品边界

### 现场可完成

1. 一键取得当前位置，并通过腾讯地图补齐地址、行政区和附近同类地点；
2. 用四步极简流程录入阶段、关键账目和三个现场答案；
3. 本地计算日保本营业额、日保本订单、月利润和现金寿命；
4. 压力 / 当前 / 改善三个场景；
5. 基于证据缺口生成“下一条最高信息量问题”；
6. 输出决策闸门、唯一下一步和明确停止线；
7. 预置一个来自语料结构的匿名演示案例。

### 不应在 Demo 中假装已经完成

- 真实人流预测；
- 全国转让费数据库；
- 自动判断食品品质；
- 对任何餐厅给出可靠营业额预测；
- 法律、财务或投资结论；
- 证明建议真的提高了存活率。

### 赛后最关键验证

不是问“老板觉得建议专业吗”，而是验证：

- 是否有 10 位准备签约的人愿意完整录入资料；
- 其中多少人因证据不足推迟或取消不可逆支出；
- 避免或延后投入的金额；
- 经营中用户是否按建议完成实验；
- 实验是否让决策从主观争论变成可核验结果；
- 30 天后仍有多少人回来看停止线。

## 9. 最适合比赛的 90 秒演示

1. 用户选择“准备开店”，点一下“使用我现在的位置”。
2. 系统通过腾讯地图显示地址、商圈线索和 800 米内同类地点，并明确这些不等于真实客流。
3. 用户填计划投入、房租、人工、固定支出、现金和客单，再回答三个现场问题。
4. 系统算出日保本 118 单，而用户对目标客群、门头可见性和真实复购仍没有证据。
5. 系统拒绝给“可以开”的长答案，输出 `STOP`。
6. 它只给一个 800 元、三天可完成的摊位 / 预售实验，并写明订单低于多少就不签约。

前后状态变化不是“用户获得了建议”，而是：

> 原本今天要不可逆地交 20 万，现在只花 800 元验证最危险的假设，并保留退出权。

这同时满足真实损失、AI 感知、系统执行、结果可测和 Demo 可见。

## 10. 最终判断

勇哥内容里最值得产品化的不是他的金句，也不是“提高营业额”的建议库，而是三件事：

1. **先把人从情绪和沉没成本中拉回现实；**
2. **用现场证据和完整账目重新定义问题；**
3. **在继续投入之前设置可验证、可退出的闸门。**

所以项目的根本使命应是：

> 不是帮助所有餐厅成功，而是让更多普通人在失败尚可承受时，及时停止一次错误下注。
